Mawzun documentation

The complete reference: the agent-facing AI API (reads and writes), the dashboard-facing Main API, every environment variable, and how to host your own Mawzun instance from scratch.

Overview

Mawzun is an Arabic-first inventory, sales and purchasing SaaS. All services share one Postgres database and never call each other — each service reads the DB directly.

ServiceDeploys toRole
BackendHeroku → api.mawzun.orgMain API (Express + Prisma). Everything the dashboard does.
app-frontendWorkers → app.mawzun.orgDashboard (TanStack Start).
home-frontendWorkers → mawzun.orgLanding site.
app-shopify-webhookWorkersHMAC-verified Shopify sync: orders create/update/cancelled, products create/update, hourly inventory push.
app-ai-apiWorkers → ai.mawzun.orgAPI-key-authenticated agent API. Read and write.
app-docsPages → docs.mawzun.orgThis page (static HTML, no build).
Money is stored as decimals (120.00). Responses are { "success": true, "data": … }. Lists are { "items": […], "count": n }. Soft-deleted rows are hidden everywhere; deletes never free unique names — reuse a name and you get 409.

Authentication

Agents (AI API)

Send the API key as a bearer token on every request:

curl https://ai.mawzun.org/v1/products \
  -H "Authorization: Bearer mz_liv...xxxx"
Keys are minted in the Mawzun dashboard → مفاتيح API. The full key is shown once at creation; store it securely. Revoking a key cuts the agent off immediately. Every request is scoped to the key's company — cross-company access is impossible by construction.

Dashboard (Main API)

POST /api/v1/auth/signup creates the account (the first account in a fresh company becomes its owner), POST /api/v1/auth/login returns data.tokens.accessToken (60 min) plus a refresh token. Send Authorization: Bearer <accessToken> on everything else. POST /api/v1/auth/refresh rotates the pair; POST /api/v1/auth/logout ends the session.

Errors & conventions

StatusMeaning
200 / 201Success / created
400Validation failed — the Arabic message says what to fix
401Missing/invalid/revoked key or expired session
404Not found in this company (ids from another company also 404 — never 403)
409Conflict: duplicate unique field, cap reached, or illegal state transition
429Rate-limited (auth endpoints) — back off for the window in Retry-After
500Internal error — retry once, then back off

Error bodies look like { "success": false, "message": "…", "data": null, "code": "CONFLICT" }. The AI API returns the message under data.error instead.

AI API — reads

Base URL https://ai.mawzun.org. Key in, company-scoped data out.

GET/v1/products?search=&limit=

List products (max 200). search filters by name.

GET/v1/products/:id

Single product with aggregate on-hand stock.

GET/v1/stock/levels?limit=&lowStock=

Stock per product per warehouse location with onHand, reserved, available and the storageLocationId needed for adjustments — plus a lowStock array (available ≤ threshold) so agents can warn about shortages. Threshold: AI_LOW_STOCK_THRESHOLD env (default 5), overridable per request with ?lowStock=.

GET/v1/orders?status=&customerId=&limit=

Recent orders; filter by status (NEW, CONFIRMED, ON_THE_WAY, DELIVERED, CANCELLED, …) and/or customerId.

GET/v1/orders/:id

Order detail with line items. :id accepts the Mawzun order number (ORD-000123), the external Shopify number, or the internal id.

GET/v1/customers?search=&limit=

Search by name or phone.

GET/v1/customers/:id

Customer detail with their 20 most recent orders.

GET/v1/notifications?limit=

Company-wide notifications (low-stock alerts, order events), newest-first. Keys see company-wide rows only.

GET/v1/coupons · /v1/coupons/:id · /v1/vendors · /v1/vendors/:id

List/get for coupons and vendors — the read half of the write endpoints below.

AI API — writes

Agents can run the business, not just report on it. Same key, same company scope, same business rules as the dashboard — totals, discounts, coupons and stock movements are computed server-side, never trusted from the request.

Products

POST/v1/products

{ name*, price?, costPrice?, skuCode?, barcode?, trackStock?, categoryId?, brandId?, uomId?, images?[] }. SKU must be unique per company (409 on clash). Money is clamped to 0…99,999,999; at most 20 images.

PATCH/v1/products/:id · DELETE/v1/products/:id

Partial update (rename regenerates the slug; archived: true/false maps to archivedAt; providing images replaces all of them). Delete is a soft delete.

Customers

POST/v1/customers · POST/v1/customers/find-or-create

{ name*, phoneNumber1*, phoneNumber2?, email?, address?, notes? }. Phone is unique per company. Find-or-create matches on phone and returns { customer, created } — the idempotent way to resolve a caller.

PATCH/v1/customers/:id · DELETE/v1/customers/:id

Coupons

POST/v1/coupons

{ code*, discountType: PERCENTAGE|FIXED, value*, minOrderTotal?, maxRedemptions?, expiresAt? }. Codes are uppercased; PERCENTAGE value must be 0…100 (enforced on create and patch).

PATCH/v1/coupons/:id · DELETE/v1/coupons/:id

Vendors

POST/v1/vendors

{ name*, kind: SUPPLIER|CONSIGNMENT, contactPerson?, phoneNumber?, email?, commissionRate? }. Balance is ledger-managed and read-only.

PATCH/v1/vendors/:id · DELETE/v1/vendors/:id

Delete is blocked with 400 while the vendor balance is non-zero.

Orders

POST/v1/orders

{ "customerId": "…", "items": [{ "productId": "…", "quantity": 2 }],
  "shippingCost": 0, "discountPercentage": 0, "couponCode": "SAVE10" }

Status is forced to NEW; the order number (ORD-000123) is generated. Per-line totals, the order total and coupon discounts are computed server-side — an invalid coupon fails the whole create with 400, and a valid one snapshots couponCode and bumps its redemption count.

PATCH/v1/orders/:id

Edit notes/address/warehouse/carrier; providing items replaces all lines and recomputes totals. Blocked with 409 on DELIVERED/CANCELLED orders.

POST/v1/orders/:id/status · POST/v1/orders/:id/cancel

{ status, cancelReasonId?, warehouseId? }. Guards mirror the dashboard: same-status and terminal states (CANCELLED, and DELIVERED which must go through returns) return 409; cancelling requires a reason; confirming an order with tracked-stock lines requires a warehouse. Confirming commits stock and cancelling/returning releases it — exactly like the dashboard confirm flow.

DELETE/v1/orders/:id

Soft delete, blocked on DELIVERED. Cancelling first restocks; deleting does not.

Stock

POST/v1/stock/adjust

{ productId*, storageLocationId*, countedQuantity* (target, not delta), reason? }. Sets the level to the counted quantity and writes the signed delta to the immutable inventory ledger. Going negative is blocked unless negative stock is allowed. A no-change count writes no movement and returns the current balance.

Notifications

POST/v1/notifications/:id/read · POST/v1/notifications/read-all · DELETE/v1/notifications/:id

What is deliberately not here, and why. countries is a global table with no companyId, so it cannot be company-scoped — exposing it would either show one tenant another's rows or let a company edit data others depend on. Product images are already covered: POST/PATCH /v1/products accept images[] and replace the set atomically. And api-keys, sessions, stores and sync-errors are operator surfaces — an API key that can mint keys or read sealed store tokens is a privilege-escalation path, not a business action.
Enum values are enforced, not advisory. An invalid value (for example "type": "EXTERNAL" on a carrier) is rejected with 400 and a message naming the allowed values — it never reaches the database, so it can never surface as a 500. The values above were read from the live database, which is the only source that is guaranteed to be right.
Names are unique per company, including after a delete. The unique index covers (companyId, name) and does not exclude soft-deleted rows, so re-creating a name you previously deleted returns 409 — the same answer the dashboard API gives. Choose a different name, or edit the existing row instead.
Decimal fields come back as strings. A numeric column (percentage, shippingCost, carrier costs) is serialised as "15.00", not 15, because a decimal cannot round-trip through a JavaScript float without losing precision. The dashboard API does the same thing. Send a number; read a string.

Main API — endpoint reference

Most resources follow one standard pattern: GET / (searchable, paginated list) · GET /:id · POST / · PATCH /:id · DELETE /:id (soft delete). Below is every domain with its full paths; anything beyond the standard five is spelled out.

Users & roles

/users — standard five, plus GET /users/check-permission, POST /users/:id/reset-password, POST /users/roles/assign. Company user cap: MAX_USERS_PER_COMPANY (default 10). /roles — standard five plus GET /roles/permissions (the permission catalog).

Catalog /catalog

/products — standard five, plus POST /:id/restore, POST /:id/archive, POST /:id/unarchive. Product images live at /products/:productId/images (POST /upload, list, add, patch, POST /:id/primary, delete). /brands, /categories, /uoms, /tax-rates, /attributes and /attributes/:attributeId/values follow the standard pattern. /merges — GET /, POST /, POST /:id/execute, POST /:id/cancel (executing moves stock and order lines to the target and archives the source).

Inventory /inventory

/warehouses, /storage-locations, /operation-types, /reorder-points — standard pattern. /stock — GET /levels, GET /transactions (immutable ledger), POST /adjust, POST /transfer. /operations — standard five plus POST /:id/validate, POST /:id/execute, POST /:id/cancel. /counts (stocktaking) — list/get/create plus POST /:id/start, POST /:id/items, POST /:id/complete, POST /:id/cancel.

Sales /sales

/customers — standard pattern plus POST /find-or-create and GET /:id/orders. /orders — list/get/create/patch/delete plus GET /:id/invoice, POST /bulk/status, POST /:id/status, GET /attention (needs-attention queue: new/no-answer/postponed/stuck counts for the sales command page). /coupons — standard pattern plus POST /redeem. /order-sources, /payment-methods, /cancel-reasons, /fulfillment-batches, /shipping-returns — standard pattern.

Purchasing /purchasing

/vendors — standard pattern (SUPPLIER | CONSIGNMENT; delete blocked on non-zero balance). /purchase-orders — standard five plus POST /:id/receive.

Production /production

/batches — standard five plus POST /:id/start, POST /:id/produce, POST /:id/complete, POST /:id/cancel. /planning — GET /needs-manufacturing, GET /deficits.

Shipping /shipping

/countries (list), /carriers, /cities, /governorates and nested /governorates/:governorateId/cities — standard pattern.

Finance /finance

/wallet — GET /summary, GET /, POST /adjustments. /payout-methods — standard pattern. /withdrawals — list/get/create plus POST /:id/approve, POST /:id/reject, POST /:id/pay.

System /system

/api-keys — standard five plus POST /:id/revoke (cap: MAX_API_KEYS_PER_COMPANY, default 5). Keys carry an optional per-key AI throttle (rateLimitMax / rateLimitWindowMs, null = worker AI_RATE_LIMIT_* defaults, 600/min); editable from the API-keys screen. /notifications — list, GET /unread-count, POST /:id/read, POST /read-all, delete. POST /uploads (max UPLOAD_MAX_BYTES, default 10 MB). /stores — full CRUD for CUSTOM | SHOPIFY stores (Shopify needs SHOPIFY_FEATURE_ENABLED=1; cap MAX_SHOPIFY_STORES_PER_COMPANY, default 3) plus POST /stores/:id/backfill (page size BACKFILL_PAGE_SIZE, max pages BACKFILL_MAX_PAGES). /sync-errors — list/get plus POST /:id/retry, POST /:id/resolve, POST /:id/ignore, POST /resolve-all. /sessions — GET / lists the caller's live sessions (device, IP, started, expires, which one is current) and DELETE /:id ends one. Holding Permissions.ManageUsers widens the list to every member's sessions in the company; without it you see only your own, because a session row carries the device and IP address. Platform-admin users and impersonation sessions are never listed. Ending another member's session writes an audit entry; ending your own is an ordinary logout. Revocation kills the refresh token — an access token already issued stays valid until it expires (JWT_ACCESS_MINUTES, default 60).

Reports /reports

/overview — /products, /inventory, /orders, /purchases, /shipping. /orders — /totals, /graph, /status-distribution, /source-distribution, /confirmed, /top-products, /top-categories, /top-employees, /top-return-reasons, /product-confirmation. /carriers — /most-used, /fastest, /success-rate, /cost-stats, /:carrierId/city-success-rate. /stock — /, /totals, GET /movements?days= (daily in/out from the ledger), GET /attention (out-of-stock + low-stock rows, open counts, pending operations).

Shopify sync (webhook worker)

Topics orders/create|updated|cancelled and products/create|update are verified by HMAC and ingested idempotently (companyId + storeId + externalId unique; replays return duplicate). Webhook registration on the merchant store is automatic when SHOPIFY_WEBHOOK_BASE_URL is set — connecting the store in Mawzun is the whole flow, no Shopify-dashboard clicking. An hourly cron pushes INVENTORY_PUSH_SKUS_PER_RUN mapped SKUs (default 250) per run for auto-sync stores.

Rate limits

Auth endpoints (/auth/login, /auth/signup, /auth/refresh, /auth/forgot-password*) are Redis-counted per IP+account (defaults: 30 per 15 minutes, successful login clears the count). Reset emails: 1 per user per 24 h. Every authenticated request: 300 per user per minute. Each limiter has its own *_DISABLED kill switch; without REDIS_URL everything fails open — a single tenant cannot starve another because every query is company-scoped and paginated.

The nine services

Mawzun is nine deployable services. They share one Postgres database and never call each other, except where a worker is given a URL to call. The public repository mirrors them as nine flat folders — one per service, each with its own package.json and its own CI workflow.

ServicePublic folderWhat it isRuntime
Backendapi/The REST API and the source of truth for all business rulesNode 22+ (Heroku)
app-frontendfrontend/The dashboard users sign in toCloudflare Workers (static)
home-frontendweb/The public marketing siteCloudflare Workers (static)
app-ai-apiapi_gateway/The AI/agent API — API-key auth, company-scopedCloudflare Worker
app-shopify-webhookshopify_integration/Receives Shopify webhooks, pushes inventoryCloudflare Worker + cron
mawzun-adminadmin/Platform-operator panel (all companies, error log)Cloudflare Worker

Order matters. The database must exist before the backend can migrate it; the backend must exist before any frontend or worker has a URL to talk to; and a worker's APP_SECRET must be byte-identical to the backend's or it cannot unseal store tokens. Install in the order below.

Installation — every service

Each service is independent: install only the ones you need. Every command below is run from inside that service's folder.

0 · Prerequisites

  • Node 22 or newer — the backend declares engines.node >= 22 and uses --env-file and the built-in test runner. Node 20 will fail at startup.
  • Git, and npm (ships with Node).
  • Postgres — any 14+ server. Local, Heroku, Neon, Supabase and RDS are all fine.
  • Cloudflare account + npx wrangler login — only for the five Workers and the two static frontends.
  • Heroku CLI — only if you deploy the backend to Heroku.
git clone https://github.com/MohamedAYassin/Mawzun.git
cd Mawzun
# the nine folders are: api frontend web api_gateway shopify_integration
#                       admin uptime api_docs cleanup_worker

1 · api — the backend do this first

The only service that owns the schema. Everything else reads the database it creates.

cd api
npm ci
cp .env.example .env      # then fill in the values below
npx prisma generate
npx prisma migrate deploy
npm run seed              # creates the owner account and demo data
npm run dev               # http://localhost:5000

Login after seeding is owner@mawzun.local / Owner@123 — change the password immediately.

Do not run the test suite against a database you care about. npm test expects a disposable database; it provisions and truncates rows. Point DATABASE_URL at a scratch database first. The suite is run with --test-concurrency=4 on purpose — each file opens its own pool, and a higher concurrency exhausts the connection limit and reports cancelled tests as passes.

heroku create your-mawzun-api

                  CORS_ORIGIN=https://your-dashboard.pages.dev

8 · cleanup_worker — retention sweeps

cd cleanup_worker
npm ci
cp .dev.vars.example .dev.vars
npx wrangler secret put HEROKU_API_TOKEN
npx wrangler secret put ADMIN_KEY          # must match the uptime worker's ADMIN_KEY
npm run deploy

Deletes rows past their retention window on a cron schedule. Each window is a plain variable in wrangler.jsonc:

VariableDefaultDeletes
SESSION_RETENTION_DAYS45Sessions that are revoked or expired
PASSWORD_RESET_RETENTION_DAYS1Used and expired password-reset tokens
NOTIFICATION_RETENTION_DAYS14Notifications — read ones only; unread rows are never touched
SYNC_ERROR_RETENTION_DAYS90Sync errors already resolved or ignored
AUDIT_LOG_RETENTION_DAYS365Audit log entries
This worker deletes data. It refuses to run against a database where row-level security is not enforced, so a misconfigured connection cannot silently wipe every company's rows. node verify-sweeps.mjs proves both sides of every retention boundary before you trust it.

9 · api_docs — this site

No build step, no dependencies. index.html is the whole site.

cd api_docs
npx wrangler pages deploy . --project-name mawzun-docs

Host the whole thing — end to end

About 30 minutes once the accounts exist. Install in the order above; this is that order compressed.

  1. Database. heroku create your-mawzun-api, then heroku addons:create heroku-postgresql:essential-0. Heroku exposes one rotating DATABASE_URL; Mawzun uses it for both roles, so tenant isolation is application-level companyId scoping. If your host gives two roles, set the restricted one as DATABASE_URL and the owner as DIRECT_DATABASE_URL for row-level-security defence in depth.
  2. Backend (api/). Set JWT_KEY, APP_SECRET, CORS_ORIGIN, PASSWORD_RESET_APP_ORIGIN. Deploy, then seed the owner and change its password.
  3. Dashboard (frontend/). Set VITE_API_ORIGIN to the backend URL, deploy, and point CORS_ORIGIN back at it.
  4. Marketing site (web/). Set VITE_APP_ORIGIN to the dashboard, deploy.
  5. Workers (api_gateway/, shopify_integration/, admin/, uptime/, cleanup_worker/). Each needs HEROKU_APP_NAME + HEROKU_API_TOKEN; the ones that unseal store tokens also need the backend's exact APP_SECRET. Deploy each with npm run deploy.
  6. Docs (api_docs/). npx wrangler pages deploy .
  7. Shopify (optional). Set SHOPIFY_FEATURE_ENABLED=1 on the backend, then connect the store in Stores with an Admin API token — webhooks register themselves. Backfill history with POST /system/stores/:id/backfill (2,500 orders per call; re-trigger to continue).
Rotation & topology rules that keep you safe: Heroku stays the source of truth for the database password — workers resolve it live, and scripts/sync-hyperdrive.mjs on a 10-minute scheduler keeps Hyperdrive in sync. Services share the database but never call each other. After Heroku rotates credentials, restart the backend dyno to pick up the new URL.

Managing keys

Create and revoke keys in the Mawzun dashboard under Apps → مفاتيح API (cap MAX_API_KEYS_PER_COMPANY, default 5). Every create/rotate/revoke is audit-logged with the acting user. Key hashes are SHA-256; expiry is checked on every request.
